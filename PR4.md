# ПР №4. Аудит событий: journalctl и auditd

## 1. journalctl — системный журнал

### Что зафиксировал журнал о команде sudo cat /etc/shadow

мая 10 14:45:31 debian sudo[3730]: egor : TTY=pts/2 ; PWD=/home/egor ; USER=root ; COMMAND=/usr/bin/cat /etc/shadow
мая 10 14:45:31 debian sudo[3730]: pam_unix(sudo:session): session opened for user root(uid=0) by (uid=1000)
мая 10 14:45:31 debian sudo[3730]: pam_unix(sudo:session): session closed for user root
Разбор полей:
- `мая 10 14:45:31` – временная метка события.
- `debian` – имя хоста.
- `sudo[3730]` – процесс и PID, выполнивший команду.
- `egor : TTY=pts/2 ; PWD=/home/egor ; USER=root ; COMMAND=/usr/bin/cat /etc/shadow` – пользователь, терминал, рабочий каталог, целевой пользователь и выполняемая команда.
- `pam_unix(sudo:session)` – событие PAM-модуля об открытии/закрытии сессии sudo.

### Ошибки в системе с последней загрузки
Критические ошибки отсутствуют. При попытке просмотра полного журнала возникает предупреждение:
Hint: You are currently not seeing messages from other users and the system.
Users in groups 'adm', 'systemd-journal' can see all messages

Это не ошибка системы, а ограничение прав обычного пользователя.

### Статистика входов
- Успешных входов: не получено (доступ к логам sshd ограничен, `journalctl _COMM=sshd | grep "Accepted"` не дал результатов).
- Неудачных попыток: не получено по той же причине.

## 2. auditd — настройка правил

### Применённые правила (вывод auditctl -l)

-w /etc/passwd -p rwa -k auth-files
-w /etc/shadow -p rwa -k auth-files
-w /etc/group -p rwa -k auth-files
-w /etc/sudoers -p rwa -k priv-files
-w /etc/sudoers.d -p rwa -k priv-files
-w /etc/ssh/sshd_config -p rwa -k ssh-config
-a always,exit -F arch=b64 -S open,openat -F success=0 -F key=access-denied
-a always,exit -F arch=b64 -S unlink,unlinkat -F key=file-delete
-a always,exit -F arch=b64 -S execve -F euid=0 -F auid!=0 -F auid!=1 -F key=priv-exec

### Разбор записи SYSCALL
Пример записи из журнала аудита:

type=SYSCALL msg=audit(10.05.2026 14:57:16.409:251) : arch=x86_64 syscall=openat success=yes exit=5 a0=AT_FDCWD a1=0x7f99996ad62a a2=O_RDONLY|O_NONBLOCK a3=0x0 items=1 ppid=3085 pid=3876 auid=egor uid=root gid=egor euid=daemon suid=root fsuid=daemon egid=root sgid=egor fsgid=root tty=pts0 ses=3 comm=suo exe=/usr/bin/sudo subj=unconfined key=watch-sudoers

| Поле | Значение | Что означает |
|------|---------|-------------|
| auid | egor | Аудируемый ID — исходный пользователь, запустивший цепочку команд (не меняется при sudo) |
| uid  | root | Реальный UID процесса (владелец) |
| euid | daemon | Эффективный UID, используемый для проверки прав доступа в момент syscall |
| comm | suo | Имя команды (сокращённое) |
| exe  | /usr/bin/sudo | Полный путь к исполняемому файлу процесса |

## 3. Расследование инцидента

### Хронология действий bob
| Время | Действие | Результат | Источник (команда поиска) |
|-------|---------|-----------|--------------------------|
| 15:18:57 | echo '#!/bin/bash' > /tmp/totally-not-malware.sh | Файл создан | `ausearch --start recent -i \| grep "totally-not-malware"` |
| 15:18:57 | cat /etc/shadow | Отказ в доступе | `ausearch -k access-denied -i` (неудачный openat) |
| 15:18:57 | ls /root | Отказ в доступе | `ausearch -k access-denied -i` |
| 15:18:57 | cat /etc/sudoers | Отказ в доступе | `ausearch -k access-denied -i` |
| 15:18:57 | cat /etc/passwd | Успешно | `ausearch -k auth-files -i` |

### Как auditd помог расследованию
- Зафиксировал все попытки доступа к защищённым файлам на уровне системных вызовов, включая неудачные.
- Позволил отследить создание подозрительного файла (`/tmp/totally-not-malware.sh`).
- Записи не зависят от того, сохранились ли логи приложений или были очищены.
- Постоянно хранится UID аудита (`auid`), что позволяет выявить истинного инициатора даже при смене пользователя через `sudo`/`su`.

### Чем auditd лучше journalctl для задач аудита безопасности
- Работает на уровне ядра, перехватывая системные вызовы; journalctl видит только то, что передали сервисы.
- Фиксирует события, которые приложения могут не логировать (например, прямой системный вызов `open`).
- Не подвержен очистке логов через `journalctl --vacuum` – аудит-лог хранится отдельно.
- Даёт детальную информацию: коды ошибок, флаги открытия, все UID/GID, что позволяет точно определить попытку НСД.
- Правила можно гибко настраивать на конкретные файлы, системные вызовы и условия.

## 5. Контрольные вопросы

**65. Чем принципиально отличается auditd от journald? Почему нельзя обойтись только journald?**
auditd работает на уровне ядра, перехватывая системные вызовы, и не может быть отключён или обойдён пользовательскими процессами. journald собирает логи от сервисов, которые могут быть неполными, подделаны или не записаны злоумышленником. Только auditd гарантирует фиксацию всех событий безопасности (доступ к файлам, изменение прав) независимо от поведения приложений.

**66. Что такое auid и почему оно важнее uid при расследовании инцидентов с sudo?**
`auid` (audit UID) – это идентификатор пользователя, изначально вошедшего в систему (login UID). Он не изменяется при использовании `sudo` или `su`. `uid` (реальный UID процесса) может меняться после повышения привилегий. Поэтому `auid` позволяет однозначно идентифицировать исходного пользователя, даже если он выполнил команды с правами root.

**67. Что означает флаг -k в правиле auditd? Для чего он используется?**
Флаг `-k` задаёт ключ (произвольную текстовую метку) для правила аудита. Используется для фильтрации событий в `ausearch` (например, `ausearch -k watch-passwd`), чтобы быстро находить записи, относящиеся к определённому правилу или группе объектов мониторинга.

**68. Чем -w (watch) отличается от -a always,exit в правилах auditd? Когда использовать каждый?**
*   `-w` (watch) – простое правило для мониторинга доступа к указанному файлу или каталогу (чтение, запись, выполнение, изменение атрибутов). Удобно для отслеживания операций с конкретными критичными файлами.
*   `-a always,exit` – правило на системный вызов, которое срабатывает при выходе из заданного вызова (например, `open`), когда выполнены условия фильтрации (архитектура, success=0, UID и т.д.). Позволяет создавать сложные сценарии: фиксировать все неудачные попытки открытия любых файлов, удаление любых файлов или выполнение команд с определёнными привилегиями.

**69. Злоумышленник удалил файл /var/log/audit/audit.log. Как это помогает ему скрыть следы и как от этого защититься?**
Удаление файла аудита уничтожает все зафиксированные события, делая невозможным восстановление его действий. Способы защиты:
*   Основной – настройка немедленной отправки логов на удалённый централизованный сервер аудита (`audisp-remote`).
*   Установка прав доступа `0600` для `root` на файл и директорию логов.
*   Использование атрибута неизменяемости: `chattr +i /var/log/audit/audit.log` (препятствует даже `root` в удалении, но logrotate не сможет работать).  
*   Настройка правила аудита на удаление самого файла (сработает, но запись может не сохраниться локально при успешном удалении).

**70. Что нужно сделать чтобы правила auditd сохранились после перезагрузки?**
Поместить правила в файл `/etc/audit/rules.d/имя.rules` (например, `security-course.rules`), затем выполнить `sudo augenrules --load` для компиляции и загрузки правил. При стандартной конфигурации auditd автоматически подгружает правила из этого каталога при старте службы.
